# 好工到四川招聘模块

这次改动直接替换 HRMS 中现有招聘页面和相关接口，复用 Taro 微信小程序、React 管理后台、Portal、Fastify、Prisma/PostgreSQL、账号权限和审计记录，不新建另一套人员数据库。品牌暂定「好工到」，首期服务成都、宜宾、绵阳等四川城市，以工厂普工、仓储物流等岗位为主；城市快捷筛选不删除其他已有岗位。

## 可使用的流程

求职者打开小程序即可浏览真实公开岗位，按城市、工种和关键词筛选。卡片直接显示工资与单位、工作地点、班次及岗位实际填写的福利。详情保留电话咨询和报名按钮；选择岗位后报名表自动带入岗位，选填内容折叠，服务和隐私同意默认不选。首次微信登录建立求职账号，首次本人报名只为全新档案原子建档并绑定账号；之后使用本人已有档案确认报名。沿用 HRMS 身份证查重要求，姓名、手机号、身份证号是现有人员建档必填项。

管理后台原有路由保持：

| 页面 | 地址 | 操作 |
| --- | --- | --- |
| 岗位发布 | `/recruitment/demands` | 新建、编辑、发布/暂停；城市、工种、工资、班次、实际福利、人数和有效期 |
| 报名跟进 | `/recruitment/progress` | 姓名/手机号、项目与状态筛选；查看报名、记录面试和跟进 |
| 推荐政策 | `/policies/referral` | 金额、有效期、在岗天数、员工类型、达成/排除条件 |
| 推荐奖励 | `/recruitment/rewards` | 条件核实、财务审批、出纳登记流水和付款凭证 |

微信小程序公开岗位、本人报名、员工推荐、供应商报人和内部运营继续使用同一套 `/api`。Portal 的求职首页、岗位详情、真实报名记录、推荐邀请同步使用 `/api/portal`；管理后台的小程序界面体验仍复用 Portal 页面，不新增静态截图式演示。

## UI 与业务约束

界面采用系统应用的信息层级：浅灰底、白色大圆角卡片、黑灰文字、蓝色主操作。第二轮结构重塑去掉首页彩色方块和重复边框，改用灰白城市分段和文字工种导航，工资数字与单位分层展示。手机首屏可看到完整岗位报名按钮，详情报名区不被底部导航遮挡。后台招聘工作面去掉重复顶部导航，表格精简；390px 手机和1440px桌面没有文档横向溢出。

福利来自实际岗位字段，不默认写包吃住。未配置联系电话或推荐政策时显示缺失，不填示例号码或奖励。正式 API 不可用时显示错误，不把浏览器本地状态当成实际报名成功。小程序和 Portal 对报名成功响应验证格式；错误网页或空结果不能误报成功。会话版本阻止退出后的晚到请求恢复旧身份，旧请求也不能清除新账号。

员工本人找工作与推荐他人分成两个入口：本人报名走 `SELF`，推荐他人走明确的 `REFERRAL`，本人报名记录与推荐记录分别查看。账号/微信登录保留岗位和推荐参数，退出或会话失效立即移除敏感页面。内部员工及外包员工按原权限推荐。一次报名只绑定一名直接推荐人，拒绝自荐、换推荐人争抢和重复计奖。报名锁定当时政策快照，后续政策改价不回写历史奖励。求职者和游客可阅读奖励说明，但不会获得员工推荐权限。

奖励依次为 `PENDING → ACHIEVED → APPROVED → PAID`，同时支持有权人员取消未发放记录。资源核实、财务审批、出纳付款分别使用 `reward:review`、`reward:approve`、`reward:pay`；`reward:read` 不授权这些写操作。自动门槛按该次报名的入职日期与规则快照的在岗天数计算；满期前离职不达标，满期后离职保留可审核权益，其他文字条件由审核人结合证据核实。付款必须记录流水号、凭证、实际日期，已发放记录不能回退、重复支付。

微信首次登录不会授予运营、供应商或员工权限，也不会凭身份证认领已有档案。无档案、无额外权限范围的临时微信求职账号，可以通过已认证的 HRMS 账号和有效微信登录凭证安全衔接；原临时账号停用并撤销旧登录凭证，业务关联账号不自动转移。历史人员或匿名已报名人员需要负责人核实并绑定本人账号；为方便后续查进度，小程序推荐先微信登录再报名。未配置真实微信凭证时明确显示尚未开通，不生成替代身份。

「已发放」是出纳对实际付款的登记，不是已接通微信转账。本次验证未执行真实付款。

## 替换顺序

1. 在测试环境检出分支 `feat/haogongdao-sichuan-recruitment`，保留既有运行配置，使用原锁文件执行 `pnpm install --frozen-lockfile`。
2. 对目标数据库先做好备份，运行只读命令 `pnpm --filter @xiangneng/api db:recruitment-preflight`。该命令只读取记录，输出阻断记录 UUID，不输出身份证/手机号或连接密码。
3. 如果存在同人同岗重复推荐，或待处理奖励的原始快照缺少明确 `retentionDays`，先由业务和财务核对。预检有阻断会退出 1；系统不会删除历史记录或擅自套当前规则。历史已经支付记录不补造凭证。
4. 预检通过后使用既有发布流程执行 `pnpm db:generate`、`pnpm db:migrate`，新增迁移为 `20261002090000_bluecollar_recruitment`。迁移仅增加结构和约束，不导入演示岗位、公司或人员。
5. 构建 API、后台、Portal 和小程序并一起替换，避免旧后台继续尝试从待达成直接发放。原业务路由和人员主档保持。
6. 正式环境保持 `AI_DEMO_MODE=false`、`VITE_PORTAL_DEMO_FALLBACK=false`。本机演示启动脚本显式开启 Portal 合成演示；不要把演示构建用于正式报名。嵌入 Portal 的服务器需配置 `VITE_PORTAL_ORIGIN` 为实际 Portal 地址。

新岗位可在后台填写成都/宜宾/绵阳等城市和工种。旧岗位没有结构化城市时按已有工作地点兼容，不改写原项目资料。

## 验证与运行

- API 最终完整单测 169 项通过（包含金额解析、首次微信登录、账号衔接与报名回归）；共享模块 8 项通过。
- 原生小程序 34 项测试、类型检查和微信构建通过，22 个页面产物完整。
- 管理后台全套测试在 `TZ=Asia/Shanghai`、单 worker 下 35 项通过；类型检查、lint和构建通过。
- Portal 16 项测试、类型检查和生产构建通过，包括正式 API 失败不转成假报名成功、小时工单位不改成月薪、空福利不补承诺、HTTP 200 无效报名结果不误报成功。
- 真实 PostgreSQL 17 隔离库 12 个集成场景通过，覆盖报名至付款的实际事务、本人/项目范围、并发推荐和付款、流水冲突回滚。旧 HRMS 升级保留财务历史数据的检查通过。另 11 项首次微信求职者及账号衔接集成验证通过，微信上游使用隔离 stub，建档、绑定、并发和本人范围使用真实数据库。
- 浏览器31项检查通过、0个JavaScript错误，覆盖手机390和桌面1440的筛选、详情、报名同意、成功后查看本人报名、生成推荐邀请及后台岗位发布；首次登录8个新会话连续进入正常。另6项账号界面检查通过，覆盖头像不退出、手机退出清缓存、无推荐权限不显示分享入口。详细报告在 `docs/reports/bluecollar-test-report.md`，UI脚本在 `tests/bluecollar/ui-smoke.mjs`。

本机开发沿用 `pnpm dev`（API3310、后台5173、Portal4320）；Windows既有演示启动沿用 `pnpm demo:start`。只体验 Portal 合成界面可显式设置 `VITE_PORTAL_DEMO_FALLBACK=true`、`VITE_DISABLE_PWA=1` 后运行 `pnpm --filter @xiangneng/portal dev`，页面明确标示演示，正式数据不依赖本地演示存储。

微信开发者工具打开 `apps/miniapp`，源码配置 `miniprogramRoot` 为 `dist/`。正式发布需要真实 AppID、服务端 AppSecret、合法 HTTPS API 域名、隐私保护指引、订阅消息等实际配置。当前 `touristappid` 只用于构建/开发预览，本次未提交微信平台审核、未替换实际服务器数据库。
