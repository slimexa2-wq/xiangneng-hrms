# 小程序报销与岗位职级权限优化说明

## 1. 本次修改目标

本次修改在保留现有后台报销模块、报销 API 和数据库业务表的前提下，完成两项主线：

1. 补齐微信小程序报销入口和移动办理链路；
2. 将内部员工岗位、职级、账号、系统角色和数据范围建立可维护的联动关系。

没有推倒现有 HRMS 架构，继续沿用 Fastify、Prisma、React、Taro 和现有 RBAC 数据模型。

## 2. 已实现功能

### 2.1 小程序报销中心

新增页面：

- `pages/reimbursements/index/index`：我的报销或报销待办列表；
- `pages/reimbursements/form/index`：创建报销草稿和多条费用明细；
- `pages/reimbursements/detail/index`：查看明细、附件、问题、审批记录和付款结果。

页面能力根据当前账号权限动态显示：

- 内部员工：创建报销、上传付款凭证与发票、提交、查看进度；
- 部门制单人：整理部门报销材料并推进制单节点；
- 部门负责人：审核报销，并受当前职级审批金额上限约束；
- 财务审核：记录问题、解决问题、财务审核和查看财务材料；
- 出纳：上传整单最终付款凭证，并登记付款日期、流水号和金额。

同一账号拥有多个角色时，管理端口与员工自助能力可以同时存在。财务人员只要同时具有内部员工角色和员工权限，仍可以使用内部推荐、工资条和个人报销，不再被单一主角色判断挡住。

### 2.2 员工自助报销归属

员工发起报销时：

- 申请人由当前登录账号确定；
- 所属中心和业务部门从已绑定的有效内部员工档案自动带出；
- 合同主体作为员工及任职记录上的独立法律关系保存，不挂在业务部门节点上，也不参与组织数据范围判断；
- 客户端不能自行改成其他业务部门；
- 未绑定内部员工档案或员工档案未绑定部门时，服务端拒绝创建报销。

这避免了员工在小程序里随意选择组织归属，也保证后续部门审批和数据范围过滤有可靠依据。

### 2.3 审核问题与补充材料

负责人或财务提出问题后，申请人可以在负责人审核或财务审核阶段补传整单辅助材料。

限制如下：

- 仅申请人本人可补传；
- 必须存在未解决问题；
- 只能上传 `SUPPORTING` 辅助材料；
- 不能在审核阶段修改原始付款凭证和发票；
- 问题解决前不能继续推进流程。

### 2.4 发票金额规则统一

报销明细规则调整为：

```text
发票金额 >= 付款金额 > 0
```

允许发票金额等于付款金额。接口、数据库约束、后台页面、演示模式、报销材料说明和测试口径已同步修改，避免不同入口互相打架。

付款登记还增加了独立的最终付款凭证约束：

- 最终付款凭证必须挂在整张报销单上，不能关联某一条费用明细；
- 费用明细中的原始付款截图不能代替财务实际打款后的最终凭证；
- 小程序、后台管理端、API 和断网演示模式均要求先上传或选择最终付款凭证，再登记流水。

### 2.5 岗位自动授权

新增 `PositionRoleBinding`：

```text
岗位 -> 系统角色 -> 默认数据范围
```

岗位配置保存后，会同步当前岗位下所有在职且已绑定系统账号的员工。岗位授权使用 `POSITION` 来源标识，系统只撤销和重建岗位来源授权，不影响人工授权和临时授权。

内部岗位支持的数据范围包括：

- 本人 `SELF`；
- 本部门 `ORG_UNIT`；
- 本中心 `CENTER`；
- 集团 `GROUP`。

`BRANCH` 仅保留给项目、招聘需求、派遣外包等经营地域场景，不能再由内部岗位自动授予。花名册中的“宜宾分公司”“绵阳分公司”等均作为业务部门节点维护。

非超级管理员或系统管理员不能通过岗位配置授予集团范围、集团负责人或总部管理者角色。前端隐藏与服务端硬校验同时存在。

### 2.6 职级报销审批策略

新增 `JobGradeApprovalPolicy`，后台可为每个职级配置报销审批金额上限，单位在数据库中为分。

- 未配置：不限制审批金额，兼容现有流程；
- 已配置：负责人审核时，若报销付款总额超过当前审批人的职级上限，服务端拒绝处理并提示由更高职级负责人审核；
- 职级策略不自动授予任何功能权限。

### 2.7 内部员工账号绑定

后台内部员工管理增加系统账号绑定、换绑和解绑能力。

- 新增员工时可直接选择未绑定账号；
- 存量员工可在详情中绑定、换绑或解绑；
- 换绑时撤销旧账号岗位授权，按当前员工岗位给新账号生成授权；
- 同一个账号不能绑定两名内部员工；
- 账号绑定操作要求同时具备内部员工维护和账号管理权限；
- 变更记录新增 `ACCOUNT_BIND`、`ACCOUNT_UNBIND` 类型。

## 3. 权限判断方式

本次将报销权限判断收敛到授权包：

```text
角色 + 该角色拥有的权限 + 该角色绑定的数据范围
```

当账号拥有多个角色时，系统不会再把“角色 A 的财务审核权限”和“角色 B 的项目范围”随意拼接。报销查询、详情、流转、问题、附件和付款操作都会先取得当前操作权限对应的授权范围，再执行服务端过滤。

同一原则也用于本次新增的权限配置入口：

- 岗位角色配置只使用 `user:manage` 权限所在授权包的数据范围；
- 员工账号绑定同时要求账号管理和员工档案维护能力，但员工可操作范围只使用 `internal-employee:write` 所在授权包；
- 其他角色拥有的更大范围不能被借用到上述操作中。

## 4. 后台配置顺序

建议按以下顺序配置：

1. 确认系统角色及角色权限；
2. 在“内部员工管理”中的岗位权限配置里，为岗位绑定角色和默认数据范围；
3. 在职级审批配置里设置需要限制的审批金额；
4. 确认内部员工已关联部门、岗位、职级；
5. 为内部员工绑定系统账号；
6. 重新登录账号，检查小程序菜单、报销列表和待办范围。

调岗时只需更新员工所属业务部门、岗位和职级，所属中心由部门层级解析，系统会刷新岗位授权。合同主体发生变化时单独更新员工和任职记录的法律主体字段；人工授权和临时授权仍需在对应权限管理入口维护。

## 5. 数据库迁移顺序

在已有迁移基础上依次执行：

1. `20260727090000_position_role_bindings`：岗位角色绑定及岗位授权来源；
2. `20260727091000_reimbursement_invoice_cover`：发票金额允许等于付款金额；
3. `20260727100000_job_grade_reimbursement_policies`：职级报销审批上限；
4. `20260727101000_internal_employee_account_binding`：账号绑定和解绑变更类型；
5. `20260727130000_internal_departments_not_branches`：将内部花名册组织统一为中心和业务部门，转换旧岗位分公司范围，移除组织单元、内部员工和任职历史中的旧分公司字段，并解除部门与单一合同主体的隐含绑定。

部署时应使用项目原有 Prisma 部署命令执行迁移并重新生成 Prisma Client，例如：

```bash
pnpm db:generate
pnpm db:migrate
```

以上命令来自根目录 `package.json`。执行迁移前应备份正式数据库。

## 6. 关键安全边界

- 小程序隐藏按钮不代表授权，所有关键操作均由 API 再校验；
- 员工自助报销组织归属不能由客户端覆盖；
- 报销权限只使用对应授权包的数据范围；
- 岗位配置不能越级授予集团范围；
- 账号换绑会刷新旧、新账号令牌，避免旧会话继续使用已撤销权限；
- 审核期间只允许受约束的辅助材料补传；
- 金额和流程版本均由服务端校验；
- 付款登记必须引用当前报销单的整单最终付款凭证；
- 岗位配置和员工账号绑定均使用对应操作权限的授权包范围，防止多角色范围交叉拼接。

## 7. 当前保留限制

本次没有擅自扩大为通用流程引擎，以下能力仍保持现状：

1. 流程仍以七态正向流转为主，尚未新增正式的退回、拒绝、撤回和代理审批节点；
2. 付款凭证包和发票包后端仍沿用现有压缩包生成逻辑，小程序提示到电脑端下载，尚未改造成真正分页排版的 PDF；
3. `CENTER` 岗位范围当前支持“中心节点本身”以及“直接归属于中心的业务部门”；更深层级组织若未来启用，需要扩展祖先链解析；
4. 没有接入 OCR、预算控制、重复发票识别和微信订阅消息；
5. 完整依赖安装、Prisma 生成、Vitest、后台构建和小程序构建需在可访问 npm 且具备项目依赖的环境执行。

这些限制不影响本次新增代码的结构检查和领域规则验证，但上线前必须完成完整环境验证。
