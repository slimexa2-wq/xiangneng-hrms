# 祥能人力资源综合信息系统总体架构

## 1. 设计结论

本系统在现有 pnpm monorepo 上增量建设，不重写现有 React、Fastify、Prisma 和 Taro 工程。PC 管理后台继续采用 React 18、Vite 和 Ant Design；浏览器中的手机演示继续由 Portal 提供；正式微信小程序由 Taro 工程构建；三端通过同一个 Fastify API 和同一套 PostgreSQL 业务数据协同。

公开演示环境只使用确定性合成数据。原始 Excel、人员清单、身份证、电话、银行卡、工资、合同和报销附件不进入公开 Git 历史、构建产物或公开数据库。

## 2. 运行架构

```text
PC 管理后台（React + Ant Design） ─┐
Portal 手机网页演示（React）      ├─ HTTPS ─> Fastify API
Taro 微信小程序                  ─┘             │
                                                ├─ 登录会话与多角色 RBAC
                                                ├─ 数据范围与字段权限
                                                ├─ 人员/项目/招聘/供应商领域服务
                                                ├─ 内部人事与组织领域服务
                                                ├─ 工资/推荐/员工服务领域服务
                                                ├─ 报销七态工作流
                                                ├─ 文件、OCR、导入导出、通知
                                                ├─ AI 受控工具适配层
                                                ├─ 审计、幂等与健康检查
                                                └─ Prisma -> PostgreSQL

Ollama / qwen3.5:4b ──> AI 意图与参数解析
本地磁盘 / 腾讯云 COS ──> FileStorage 抽象
```

## 3. 模块边界

### 3.1 组织与内部人事

- 法人主体、分公司、中心、部门、岗位、职级形成组织树。
- 内部员工使用独立的 `InternalEmployee` 主档，并可关联登录账号。
- 任职、调动、停用、离职通过变动记录驱动，不允许直接覆盖历史。
- 调动事务同时结束旧任职、创建新任职、撤销旧范围授权并写审计。
- 只有不存在账号、任职、业务单据和审计关联的错误建档记录允许物理删除。

### 3.2 派遣人员、项目与招聘

- 现有 `Person` 继续作为求职者、派遣或外包人员主档。
- 报名、面试、待入职、在职、离职由状态日志形成生命周期。
- 项目、岗位需求、供应商、报名、推荐、工资条沿用现有模型并补充约束、索引和服务边界。
- 现场运营端只操作被授权项目范围内的人员。

### 3.3 报销

- 报销必须关联内部员工和组织，不另建人员库。
- 一笔费用只录入一次；管理端从已提交明细自动生成三张表。
- 正式状态固定为：待提交、部门制单中、负责人审核中、财务审核中、审核通过、待打款、已打款。
- 问题标记独立于主状态；存在未解决问题时不得进入审核通过。
- 付款凭证与发票分别生成打印包，均按同一明细编号排序。
- 所有推进使用短事务、版本号、幂等键和状态前置条件。

### 3.4 AI 业务助手

- 规则路由优先，本地模型只在复杂语义时解析意图和参数。
- 模型不持有数据库连接，不生成自由 SQL，不直接执行确认。
- 查询工具从真实登录态计算权限范围，返回最新数据库结果。
- 写操作先返回绑定用户、过期时间和 token 的预览；用户点击确认后后端重新读取状态并在事务中执行。
- 本地默认模型为 `qwen3.5:4b`；模型超时、不可用或输出不通过 Schema 时回退到规则路由和结构化表单。

## 4. API 约定

- 所有业务接口使用 Zod 校验输入。
- 错误响应包含稳定错误码、可读消息和 `requestId`，不暴露数据库字段、SQL 或模型提示词。
- 列表接口默认使用游标分页；兼容现有页码接口时设置最大页深并提供下一页游标。
- 独立查询并行启动，避免请求瀑布。
- 写操作在服务层完成事务，不在路由中拼装跨领域数据库写入。
- 文件上传先写临时对象，业务事务成功后绑定；失败时由清理任务回收孤儿对象。

## 5. 稳定性与隔离

- `APP_ENV=demo` 只能连接独立演示数据库，重置接口在其他环境拒绝执行。
- 健康检查覆盖 API、数据库、迁移、文件存储、Ollama 和 AI 工具注册表。
- AI、OCR、通知和云存储故障不得阻断传统业务查询与人工流程。
- 数据库连接使用连接池；应用账号不使用 PostgreSQL 超级用户。
- 上传下载、导入导出、权限变化、人员变动、报销状态变化和 AI 写操作全部进入审计日志。

## 6. 部署拓扑

### 本地比赛环境

- PostgreSQL、API、后台、Portal、小程序构建和 Ollama 均在本机运行。
- 一键启动脚本进行迁移、合成 Seed、模型预热和健康检查。
- 断网时规则路由、数据库查询、入离职预览确认和传统业务流程仍可运行。

### 公开演示环境

- 部署后台静态站、Portal 静态站、Fastify API 和独立 PostgreSQL。
- 只导入确定性合成 Seed，不上传真实附件。
- AI 默认运行规则与工具模式；配置受信任的兼容模型服务后才开启语义兜底。

### 生产准备

- 数据库、COS、域名、HTTPS、微信 AppID 和上传私钥全部通过环境变量或密钥管理注入。
- 仓库只提供配置模板和自动化脚本，不提交任何密钥。
